# Site Storyboard

Этот документ описывает структуру будущего лендинга как последовательность экранов и пользовательский сценарий.

Использовать вместе с:
- `docs/PROJECT-DIRECTION.md`
- `ui-kit/`

## Общая драматургия

Пользователь проходит путь:

**Хочу автомобиль → вижу реальные варианты → понимаю процесс → считаю стоимость → убеждаюсь в реальности сервиса → снимаю риски → оставляю заявку.**

Сайт должен восприниматься как единая история, а не как набор независимых секций.

## Сквозной объект

Через весь сайт проходит один демонстрационный автомобиль.

Рабочий placeholder:
- модель: Xiaomi SU7;
- страна: Китай;
- lot ID: CN-18402;
- статус: меняется по ходу страницы;
- маршрут: China → Russia;
- ETA: демонстрационный диапазон, если нет реальных данных.

Этот автомобиль используется:
- в Hero;
- в блоке актуальных автомобилей;
- в «Пути автомобиля»;
- в конфигураторе;
- в live-content;
- в финальном CTA.

Если позже появится реальный кейс, placeholder заменить на реальные данные.

# 01. Hero

## Задача

За первые секунды объяснить:
- что сайт про импорт автомобилей;
- что процесс управляемый и прозрачный;
- что пользователь может рассчитать и заказать автомобиль.

Hero должен быть эмоциональным, но не превращаться в технологическую демонстрацию.

## Контент

Основной оффер:
- доставка автомобилей из Китая / Азии в Россию;
- понятная стоимость;
- прозрачный маршрут;
- контроль сделки.

Пример служебных данных:
- `XIAOMI SU7 / CN`
- `ROUTE / CHINA → RUSSIA`
- `STATUS / IN TRANSIT`
- `ETA / 18–28 DAYS`

Не показывать фиктивные данные как реальные.

## CTA

Primary:
- «Рассчитать автомобиль»

Secondary:
- «Смотреть автомобили»

## Визуальная композиция

- крупный автомобиль;
- много свободного пространства;
- большой editorial heading;
- маршрутные и статусные данные поверх или рядом;
- один сильный визуальный акцент;
- background может быть видео, image-sequence или статичным cinematic image.

Не использовать Three.js без реальной необходимости.

## UI-kit

- `btn-primary`
- `status`
- `route-card`
- mono/data typography
- display typography

## Motion

- masked text reveal;
- лёгкое движение background / автомобиля;
- появление status/ETA;
- маршрутная линия может мягко «собираться».

Motion должен начинаться сразу, но не мешать чтению.

## Реальные материалы

Желательно:
- качественное видео автомобиля;
- либо серия кадров;
- либо качественный автомобильный визуал.

# 02. Proof Strip / Быстрое доказательство

## Задача

После эмоционального Hero быстро ответить:
«Почему я должен доверять этому сервису?»

## Контент

3–5 коротких доказательств:
- договор;
- страховка;
- сроки;
- количество доставленных авто;
- регионы доставки;
- прозрачные этапы оплаты.

Цифры использовать только подтверждённые.

## CTA

Необязателен.

Допустимо:
- «Смотреть договор»
- «Как проходит сделка»

## Визуальная композиция

- компактный горизонтальный блок;
- data-driven UI;
- крупные цифры + короткие подписи;
- можно использовать marquee или live ticker.

## UI-kit

- `metric-card`
- `status`
- mono labels
- marquee

## Motion

- мягкий number reveal;
- continuous marquee;
- без тяжёлого scroll-lock.

## Реальные материалы

- подтверждённые цифры;
- юридические формулировки;
- ссылки на документы.

# 03. Актуальные автомобили

## Задача

Показать сам продукт и дать пользователю эмоциональную точку входа.

Не делать фальшивый склад.

## Формулировка

Вместо «В наличии» использовать:
- «Что сейчас можно привезти»
- «Примеры актуальных предложений»
- «Автомобили, которые можем подобрать»

## Контент карточки

- фото;
- модель;
- год;
- пробег;
- тип двигателя;
- страна;
- ориентировочная цена;
- статус;
- срок доставки.

Пример статуса:
- `AVAILABLE / CHINA`
- `CHECKED`
- `ON REQUEST`

## CTA

На карточке:
- «Рассчитать этот автомобиль»
- «Подробнее»

Блок:
- «Подобрать другой автомобиль»

## Визуальная композиция

- 3–6 крупных карточек;
- одинаковое соотношение медиа;
- единый стиль фото;
- допускается горизонтальный drag/slider;
- не превращать в каталог-маркетплейс.

## UI-kit

- `car-card`
- `media-tag`
- `status`
- custom cursor только внутри media area

## Motion

- image zoom on hover;
- drag / horizontal motion;
- статус может обновляться при hover/focus.

## Реальные материалы

Нужны:
- реальные фотографии;
- реальные или честно помеченные примерные цены;
- реальные характеристики.

# 04. Путь автомобиля

## Задача

Главный интерактивный блок сайта.

Объяснить весь процесс и снять страх неизвестности.

## Этапы

1. Подбор.
2. Проверка / видеоотчёт.
3. Выкуп.
4. Страхование.
5. Доставка до границы.
6. Таможня.
7. ЭПТС.
8. Доставка клиенту.

## Контент

Для каждого этапа:
- название;
- короткое объяснение;
- статус;
- срок;
- photo/video;
- документ / artefact при необходимости.

## CTA

Внутри блока CTA не обязателен.

В конце:
- «Рассчитать свой маршрут»

## Визуальная композиция

Sticky section.

Вариант:
- слева / сверху маршрут;
- marker или автомобиль движется по пути;
- справа меняется карточка текущего этапа;
- background/media тоже могут меняться.

## UI-kit

- `route-card`
- `status`
- glass-card
- mono/data
- marquee

## Motion

Scroll-driven:
- progress 0–1;
- marker движется по маршруту;
- этап подсвечивается;
- data card меняется;
- media синхронизируется.

Не использовать opacity как единственный эффект.

## Реальные материалы

Желательно:
- видеоосмотр;
- фото площадки;
- фото погрузки;
- таможенные документы;
- фото выдачи.

# 05. Конфигуратор стоимости

## Задача

Главный conversion-блок.

Не делать стандартный quiz.

Пользователь должен чувствовать, что управляет параметрами автомобиля.

## Структура

### Шаг / блок 1
Автомобиль:
- модель;
- тип кузова;
- EV / Hybrid / ICE.

### Шаг / блок 2
Состояние:
- новый;
- б/у.

### Шаг / блок 3
Бюджет:
- до 3 млн;
- 3–5 млн;
- 5+ млн;
- custom.

### Шаг / блок 4
Город доставки.

### Шаг / блок 5
Контакт.

## Визуальный breakdown

Справа или снизу:

```text
AUTO PRICE        ≈ 2 180 000 ₽
LOGISTICS         ≈   210 000 ₽
CUSTOMS           calculating
RECYCLE FEE       calculating
────────────────────────────
ESTIMATED TOTAL   2.8–3.2M ₽
```

Если нет точной формулы:
- показывать диапазон;
- не выдавать расчёт за точный;
- объяснить зависимость от курса и параметров.

## CTA

- «Получить точную смету»
- «Зафиксировать расчёт»

## Визуальная композиция

- большая панель;
- слева controls;
- справа breakdown;
- выбранный автомобиль остаётся видимым;
- состояние интерфейса меняется без перезагрузки.

## UI-kit

- inputs;
- chips;
- status;
- buttons;
- data table;
- route/data styles.

## Motion

- плавная смена значений;
- progress;
- loading-state:
  «Рассчитываем логистику, пошлину и утильсбор…»

## Реальные материалы

Позже:
- реальная формула;
- API курса;
- таблицы пошлин;
- реальные тарифы логистики.

# 06. Live / Bento Trust

## Задача

Доказать, что сервис существует в реальности и выполняет то, что обещает.

Это один из блоков с самым высоким приоритетом.

## Типы карточек

Поддержать несколько типов:
- `video-report`
- `vehicle-photo`
- `document`
- `metric`
- `client-review`
- `telegram-post`
- `delivery-photo`
- `manager-report`

## Контент

Пример Bento:
- большая карточка: видеоосмотр автомобиля;
- вертикальная: Telegram / short;
- квадратная: метрика;
- горизонтальная: автовоз / граница;
- документ: ЭПТС / договор;
- выдача клиенту.

## CTA

- «Смотреть больше отчётов»
- «Telegram»
- «YouTube»

## Визуальная композиция

Асимметричная CSS Grid.

Bento должен быть контентным, а не декоративным.

## UI-kit

- media cards;
- metric-card;
- glass overlays;
- status;
- custom cursor внутри video cards.

## Motion

- hover preview;
- play-state;
- лёгкий media zoom;
- drag only where relevant.

## Реальные материалы

Очень нужны реальные:
- видео;
- фото;
- документы;
- посты;
- отзывы.

# 07. Безопасность сделки

Закрыть ключевые страхи клиента.

## Основные страхи

- «Что будет с деньгами?»
- «Что если машина окажется другой?»

- «Что если задержат?»
- «Кто оформляет документы?»
- «Как я понимаю, где автомобиль?»

## Контент

- договор;
- страхование;
- фото / видеоотчёты;
- проверка перед покупкой;
- этапность платежей;
- документы;
- tracking/status.

## CTA

- «Посмотреть договор»
- «Задать вопрос»

## Визуальная композиция

Не обязательно Bento.

Лучше:
- крупная editorial композиция;
- 3–4 сильных аргумента;
- document preview;
- небольшие status markers.

## UI-kit

- status;
- document card;
- metric;
- buttons.

## Motion

Минимальный:
- document reveal;
- status change;
- hover/focus.

# 08. Отзывы / Кейсы

## Задача

Подтвердить опыт через конкретные истории.

## Контент

Лучше один отзыв = один кейс:
- клиент;
- город;
- модель;
- фото автомобиля;
- короткая цитата;
- срок;
- итоговая стоимость при наличии;
- видео при наличии.

## CTA

- «Смотреть все отзывы»
- «Смотреть кейс»

## Визуальная композиция

- masonry / editorial grid;
- не делать 6 одинаковых карточек;
- фото 1:1 или вертикальные;
- можно использовать horizontal drag.

## UI-kit

- review card;
- media;
- status;
- data labels.

## Motion

- drag;
- hover;
- image zoom;
- без тяжёлых scroll effects.

Простой accordion.

- accordion;
- focus states;
- buttons.

## Motion

- height / content reveal;
- keyboard accessible.

# 10. Final CTA

## Задача

Закрыть историю сайта и вернуть пользователя к действию.

## Идея

Сквозной автомобиль «доехал».

Статус:
- `READY FOR HANDOVER`
или
- `DELIVERY COMPLETE`

## Контент

Большой heading:
- финальная мысль про автомобиль;
- короткий текст;
- CTA.

## CTA

Primary:
- «Рассчитать автомобиль»

Secondary:
- «Подобрать модель»

## Визуальная композиция

- автомобиль в финальной точке;
- крупная типографика;
- route завершён;
- минимальное количество элементов.

## UI-kit

- button;
- status;
- mono/data;
- hero-scale typography.

## Motion

- route reaches 100%;
- status changes to final;
- автомобиль / визуал приходит в конечное состояние.

# Сквозные правила контента

## Не выдавать placeholder за факт

Если данные демонстрационные:
- явно маркировать;
- не использовать конкретные обещания без подтверждения.

## Реальные данные предпочтительнее

Приоритет:
1. реальные автомобили;
2. реальные видео;
3. реальные документы;
4. реальные отзывы;
5. только потом stock/placeholders.

# Сквозные правила motion

Motion должен:
- объяснять;
- показывать состояние;
- показывать путь;
- показывать изменение данных.

Motion не должен:
- существовать ради эффекта;
- мешать чтению;
- ломать навигацию;
- ухудшать performance.

# Критерий готовности экрана

Экран считается готовым, когда:
- понятна его задача;
- есть финальная композиция;
- есть CTA;
- определены данные;
- определены UI-kit компоненты;
- определён motion;
- определены реальные материалы;
- проверен desktop;
- проверен tablet/mobile;
- нет конфликта с соседними секциями.
