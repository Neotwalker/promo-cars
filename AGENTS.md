# AGENTS.md

Обязательные правила разработки этого репозитория.

Перед изменениями сайта читать:
1. `docs/PROJECT-DIRECTION.md`
2. `docs/SITE-STORYBOARD.md`
3. `docs/DEVELOPMENT-GUIDELINES.md`

## Source of truth

- `/ui-kit/` — дизайн-система и переиспользуемые компоненты.
- `/prototype/` — структурный прототип, не финальный production-код.
- `/live/` — рабочая финальная версия сайта.
- `docs/PROJECT-DIRECTION.md` — принципы проекта.
- `docs/SITE-STORYBOARD.md` — архитектура страницы.
- `docs/DEVELOPMENT-GUIDELINES.md` — правила качества кода.

## Обязательные правила

1. Не накапливать patch-overrides. Исправление должно заменять старую реализацию.
2. Не добавлять второй/третий CSS-блок для того же компонента в конце файла вместо редактирования исходного блока.
3. Не использовать `!important` как способ победить каскад. Исключение должно быть обосновано в комментарии.
4. После изменения удалять устаревший CSS, JS, HTML и комментарии.
5. Не оставлять debug-код, `console.log`, временные listeners и тестовые DOM-элементы.
6. Не создавать новую реализацию компонента, если она уже есть в UI-kit.
7. Повторно используемый новый компонент сначала согласовать с UI-kit или оформить совместимо с ним.
8. Не добавлять библиотеку или framework ради одного эффекта без явной необходимости.
9. Не ломать рабочие соседние секции при локальной правке.
10. Не менять одновременно несвязанные части сайта без необходимости.
11. Все интерактивы должны поддерживать keyboard/focus и `prefers-reduced-motion`, где это применимо.
12. Desktop строится на общей fluid-rem системе. До 1100px используется отдельная tablet/mobile композиция.
13. Не смешивать хаотично `px`, `vw`, `clamp()` и `rem` для связанных размеров одной desktop-композиции.
14. Не выдавать placeholder-данные за реальные факты.
15. Перед каждым коммитом в `/live/` пройти checklist из `docs/DEVELOPMENT-GUIDELINES.md`.
16. Не объявлять исправление проверенным, пока не проверены фактический код, деплой и затронутые состояния.

## Правило локального исправления

Если найден баг:

- найти исходную причину;
- найти все правила/обработчики, относящиеся к компоненту;
- изменить существующую реализацию;
- удалить конфликтующие старые правила;
- проверить desktop/tablet/mobile;
- проверить hover/focus/active/reduced-motion;
- только затем коммитить.

Запрещённый подход:

```css
/* old component */
.component { ... }

/* fix */
.component { ... }

/* fix 2 */
.component { ... !important }
```

Правильный подход:

```css
.component {
  /* одна актуальная реализация */
}
```

## Scope discipline

Для задачи «исправить X» менять только X и непосредственно зависимые части.

Если в процессе обнаружена отдельная проблема:
- не исправлять скрытно в том же коммите;
- зафиксировать отдельно;
- выполнить отдельным изменением, если это необходимо.

## Definition of done

Изменение готово только если:
- нет дублирующей старой реализации;
- нет мёртвого кода;
- нет временных debug-элементов;
- нет необоснованных `!important`;
- нет console errors;
- responsive не сломан;
- keyboard/focus не сломан;
- reduced-motion не сломан;
- публичная версия действительно задеплоена, если изменение должно быть опубликовано.
